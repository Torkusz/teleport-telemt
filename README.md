# telemt-panel

Веб-панель для MTProto-прокси [telemt](https://github.com/telemt/telemt): несколько инстансов (порт + маскировочный домен **или WEB-режим**),
пользователи и ссылки, статистика, диагностика, логи. Всё в одном Docker-контейнере.

## Запуск

```bash
cp .env.example .env          # по желанию задайте PANEL_PASSWORD
docker compose up -d --build
docker compose logs telemt-panel | grep -i пароль   # если пароль не задан — он сгенерирован
```

Панель слушает только `127.0.0.1:8080`. Заходите через SSH-туннель — так страница входа не видна зондам:

```bash
ssh -L 8080:127.0.0.1:8080 user@SERVER      # затем откройте http://localhost:8080
```

В панели нажмите **«Быстрый старт»**: откроется список портов и доменов. Это только пример — меняйте значения,
добавляйте и удаляйте строки. Один инстанс можно создать вручную с любым портом и SNI **или в режиме WEB**.

## WEB-прокси (tg://webproxy) — новое

С августа 2026 в Telegram появился транспорт **WEB Proxy**: MTProto-поток упаковывается в обычный HTTPS/WebSocket
к вашему домену на порту 443. Для DPI это выглядит как заход на сайт.

Telemt (с версии **≥ 3.5.5**) реализует WEB-режим нативно. Панель умеет создавать такие инстансы.

### Как включить в панели

1. **Система → Адрес в ссылках** — укажите ваш FQDN (обязательно для WEB).
2. Создайте инстанс → **Транспорт: WEB (tg://webproxy)**.
3. По желанию задайте `base_path` (например `tg` или `telegram/web`) — тогда прокси живёт только под этим путём, остальной сайт может быть обычным.
4. Сохраните. Telemt начнёт слушать `127.0.0.1:18080+id`.
5. Caddy панели уже проксирует 443 → этот loopback-порт (свой nginx/HAProxy — только при `CADDY_MANAGE=0`).
6. Раздайте ссылки вида `tg://webproxy?server=ваш.домен&secret=dd…` (или с path).

Клиенты: **Telegram Desktop 7.1+**, свежие Android; iOS — по мере обновлений. Звонки через WEB пока не работают.

### Минимальный nginx для WEB-инстанса

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      "";
}

upstream telemt_web_1 {
    server 127.0.0.1:18081;   # = WEB_LISTEN_BASE + id инстанса
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name proxy.example.com;
    ssl_certificate     /etc/letsencrypt/live/proxy.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/proxy.example.com/privkey.pem;

    # Carrier-пакеты до 2 MiB
    client_max_body_size 4m;

    # Весь vhost (base_path пустой) — или только location ^~ /telegram/web/
    location / {
        proxy_pass http://telemt_web_1;   # без URI — path уходит как есть
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;  # ровно один адрес
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 90s;
        proxy_send_timeout 90s;
        proxy_buffering off;
        proxy_request_buffering off;
        access_log off;
    }
}
```

Если `base_path = "telegram/web"`, замените `location /` на `location ^~ /telegram/web/` (и точный `location = /telegram/web` на decoy/сайт).

Подробности протокола и edge-cases: [документация telemt WEB](https://github.com/telemt/telemt/blob/main/docs/WEB/WEB_PROXY.ru.md),
статьи: [Habr — тестируем WEB-proxy](https://habr.com/ru/companies/domclick/articles/1092986/),
[Код.ру — как устроен tproxy](https://kod.ru/telegram-web-proxy-tproxy-server-podrobnosti).

> Официальный proof-of-concept от команды Desktop: [telegramdesktop/tproxy-server](https://github.com/telegramdesktop/tproxy-server).
> Telemt — полноценная production-реализация того же контракта.

## Каскад: РФ (entry) → зарубежный (exit)

Клиент всегда подключается к **российскому** серверу по **WEB** (`tg://webproxy`).  
Исходящие соединения telemt к DC Telegram идут через **зарубежный VPS** по **SSH-туннелю**:

```
Клиент ──WEB/HTTPS──► РФ (панель + telemt + Caddy)
                           │  telemt → 127.0.0.1:19300+id  (локальный конец туннеля)
                           │  ssh -N -L … (держит и перезапускает панель)
                           ▼
                      Abroad VPS (exit-setup.sh): sshd → SOCKS5 на 127.0.0.1:1080
                           │
                           ▼
                      Telegram DC
```

**Почему SSH, а не голый SOCKS5.** SOCKS5 не шифруется: IP назначения (например 149.154.167.51) идёт открытым текстом.
На пути из РФ такие запросы могут молча дропаться — CONNECT зависает без ответа, при этом `1.1.1.1` и запросы по имени проходят.
Внутри SSH этого не видно. Бонус: SOCKS на exit слушает только localhost и не торчит в интернет.

### Как настроить

1. На **РФ** поднимите панель, домен, WEB-инстанс (как обычно). После обновления пересоберите образ: `docker compose build --no-cache && docker compose up -d` (в образ добавлен `openssh-client`).
2. В панели: **Каскад / exit** (или карточка инстанса → Настройки → Каскад) → **Скрипт для зарубежного VPS** → скопируйте. В скрипт уже вшит публичный ключ панели (пара ключей создаётся в `/data/ssh`).
3. На **зарубежном** VPS (root) выполните скрипт. Он ставит Docker/sshd при необходимости, создаёт пользователя `telemt-tunnel` (без shell, только проброс на `127.0.0.1:1080`), поднимает microsocks на localhost и проверяет доступ к Telegram DC.
4. Из вывода возьмите `upstream_host` и `ssh_port`.
5. В панели включите **Каскад** и **SSH-туннель**, впишите Exit host, SSH порт, SOCKS порт (1080), **Сохранить**. Дальше панель сама поднимает туннель, перезапускает его при обрывах и запускает telemt после того, как локальный порт открылся. Строки `[tunnel]` видны в логах инстанса.
6. Ссылка `tg://webproxy?...` **не меняется**. Меняете только exit — клиентам ничего не шлёте.

### Несколько exit'ов (балансировка и отказоустойчивость)

В настройках каскада можно добавить до 8 exit'ов. Для каждого панель поднимает **свой SSH-туннель** и добавляет в `telemt.toml` отдельный `[[upstreams]]` с указанным **весом**:

```
exit #1  127.0.0.1:19300+id        weight 10   ┐
exit #2  127.0.0.1:19400+id        weight 10   ├─ telemt распределяет новые соединения по весу
exit #3  127.0.0.1:19500+id        weight 5    ┘  (10:10:5 → 40% / 40% / 20%)
```

- На каждом зарубежном VPS выполните свой скрипт («Скрипт» в строке exit'а): он добавляет ключ панели и поднимает localhost-SOCKS. Ключ панели один на все exit'ы.
- Кнопка **«Проверить exits»** делает SOCKS5 CONNECT на DC Telegram через каждый туннель и показывает ✓ с задержкой или причину сбоя.
- Туннели независимы: если оборвался один, перезапускается только он, остальные продолжают работать. Статус «подняты N из M» виден в настройках и на карточке инстанса.
- Галка у exit'а отключает его без удаления. Любое изменение списка exit'ов перезапускает telemt (upstream'ы не перечитываются на лету, соединения клиентов при этом переподключаются).
- Отказоустойчивость на стороне telemt (исключение упавшего exit'а из выбора) зависит от версии: проверьте на своей, остановив на одном exit'е контейнер `telemt-exit-socks` и посмотрев, остаются ли ошибки у клиентов (`docker logs` / логи инстанса). Туннель до упавшего exit'а панель будет переподнимать сама.
- Новые соединения клиентов могут уходить через разные exit'ы, поэтому IP, с которого Telegram видит клиента, у разных соединений может отличаться. Для MTProto-прокси это нормально.

Смена зарубежного сервера: новый VPS → скрипт → обновить host/порт в панели → Save.  
Если exit переустановили на тот же IP, нажмите **Сбросить ключ хоста** в настройках каскада.  
При каскаде `use_middle_proxy` и ad_tag отключаются (нужен прямой путь через ваш exit).

Режим без туннеля (прямой SOCKS5 с логином/паролем) остался для сетей, где он работает: снимите галку «SSH-туннель». Существующие инстансы со старым каскадом продолжают работать как раньше, пока вы сами не включите туннель.

Диагностика: на exit `ss -ltn | grep 1080` (должен слушать только 127.0.0.1), `docker logs telemt-exit-socks`; на РФ-стороне  
`curl -v -x socks5h://127.0.0.1:<19300+id+100*N> --connect-timeout 10 telnet://149.154.167.51:443 </dev/null` (N = 0 для первого exit'а, 1 для второго и т.д.) — должно быть `SOCKS5 request granted`.

Файлы: `exit-setup.sh` в корне репозитория (единый источник, панель подставляет в него свои значения); API `POST /api/cascade/exit-script`, `POST /api/instances/{id}/exits/check`, `GET /api/instances/{id}/cascade/script`, `GET /api/cascade/ssh-pubkey`, `POST /api/instances/{id}/tunnel/reset-hostkey`.

## Рекомендации по обходам (ноябрь 2026)

| Приоритет | Что использовать | Когда |
|-----------|------------------|--------|
| **1** | **WEB (tg://webproxy)** на своём домене + реальный decoy-сайт | Агрессивный DPI, блокировки MTProto/FakeTLS |
| **2** | **FakeTLS (ee)** + хороший SNI (CDN/Apple/Microsoft) + mask на свой сайт | Клиенты без WEB, запасной канал |
| **3** | Несколько портов (443, 5223, 8443…) с разными SNI | Один порт/домен «потушили» |
| **4** | Публичные списки прокси | Только как временный fallback — их быстро режут |

Практические советы:

- **Свой сервер + свой домен** надёжнее любых бесплатных списков.
- Для WEB: домен должен резолвиться в IP сервера, сертификат валидный, на 443 отвечает «нормальный» сайт (decoy), если capability неверный.
- Не ставьте лишний прокси *перед* WEB-endpoint без необходимости (Host/capability должны совпадать).
- В панели включите sysctl (keepalive + BBR) и rate-limit SYN — это уже есть в «Система».
- Обновляйте telemt из панели (Система → telemt) — WEB и исправления DPI появляются в релизах.
- Звонки: только через SOCKS5/VPN; MTProxy/WEB их не несут.

## Всё управление — в панели

Кнопка **«Система»**:

- **Адрес в ссылках** — домен или IP (обязателен для WEB).
- **Сеть и файрвол хоста** — быстрый keepalive и BBR; открытие портов инстансов; лимит 1 SYN/сек на IP.
  Правила живут в отдельной цепочке `TELEMT_PANEL` (UFW не трогается), панель сверяет их каждые 30 секунд.
- **telemt** — версия, проверка и обновление до последней одной кнопкой.
- **Пароль панели** — смена без перезапуска.

Если у хостера есть облачный файрвол, порты нужно открыть и в нём — панель до него не дотянется.
Для WEB достаточно открыть 80/443 (для ACME и HTTPS).

## Что внутри

- `network_mode: host` — чтобы порты добавлялись из панели без пересоздания контейнера, а UFW-правила действовали
  (опубликованные порты Docker обходят UFW).
- Панель — источник истины: пишет `telemt.toml` атомарно. Пользователи подхватываются telemt на лету, смена порта/SNI/MSS/transport — рестарт.
- Control API каждого инстанса — только `127.0.0.1` + случайный `auth_header`.
- Контейнер: `cap_drop: ALL` + `NET_BIND_SERVICE`, `NET_ADMIN`, `NET_RAW` (для iptables/sysctl хоста), read-only rootfs.
- Данные — в `./data` (state.json, конфиги, кэш TLS-эмуляции). Бэкап = копия этой папки.

## Обновление

telemt — из панели (Система → telemt). Саму панель: `git pull && docker compose up -d --build`.

## Сайт-прикрытие и сертификат (Caddy встроен в панель)

Caddy входит в образ панели и запускается ею самой, ставить его на хост не нужно:

1. В **Система** укажите **домен** (поле «Адрес в ссылках») и, по желанию, **email** для Let’s Encrypt.
2. Панель генерирует `data/caddy/Caddyfile`, запускает Caddy и открывает порты 80 и 443 в своём файрволе.
3. Caddy поднимает сайт-прикрытие (`data/sites/default`, свой сайт загружается в **Система → Сайты**) на вашем домене и **сам получает и продлевает сертификат** Let’s Encrypt (запасной вариант — ZeroSSL). Сертификаты лежат в `data/caddy-storage` и переживают пересборку образа.
4. При любых изменениях (домен, WEB-инстансы, base_path) конфиг применяется автоматически, кнопка Reload нужна только для ручного перезапуска.
5. Статус виден на главной (блок «Сайт и сертификат») и в **Подробнее**: запущен ли Caddy, совпадает ли A-запись домена с IP сервера, какой сертификат реально отдаёт сайт (панель делает настоящий TLS-запрос с полной проверкой цепочки), лог Caddy.

Что нужно для сертификата:

- A-запись домена указывает на IP этого сервера (иначе Let’s Encrypt не подтвердит домен).
- Порты **80 и 443** открыты (в файрволе хостера и в ufw, если он есть) и **не заняты**. Для голого IP публичный сертификат автоматически не выпускается, нужен домен.
- Если на 443 уже слушает FakeTLS-инстанс telemt, Caddy **не запускается**, чтобы не отнять у него порт (причина показана в панели). Выберите другой порт для инстанса или используйте WEB-режим.
- Свой Caddy/nginx на 80/443? Задайте `CADDY_MANAGE=0` в `.env`: панель будет только писать `data/caddy/Caddyfile`, а запуск и reload остаются за вами (`caddy run --config ./data/caddy/Caddyfile`).

Укажите **домен** и **email** (для Let’s Encrypt) в Системе. Кнопка **WEB-прокси** создаёт инстанс в один шаг.
